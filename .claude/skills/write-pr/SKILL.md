# PR を書く

チームの全員が同じ形で PR を書くためのやり方。レビューする人が「何が変わったか」「どう確かめたか」をすぐ読めるようにする。

## 手順

1. 変更を読む
   - `git status` で、コミットしていない変更が残っていないか見る。残っていたら、コミットするかを人に聞く。
   - `git log main..HEAD --oneline` と `git diff main...HEAD` で、このブランチで変えたことを読む。
   - 今いるブランチが `main` なら止める。main で PR は出さない。ブランチを切るかを人に聞く。
2. テストを動かす
   - CLAUDE.md の「確かめ方」に書いてあるコマンドでテストを動かし、結果（通ったか、何件か）を控える。落ちたら PR を出さず、人に知らせる。
   - コマンドが書かれていなければ、推測で動かさず、どう動かすかを人に聞く。
3. どう確かめたかを人に聞く
   - 「アプリで何を操作して、何を確かめましたか」と人に聞く。人が答えたことだけを書く。
   - 人が確かめていないことを「確かめた」と書かない。Claude が想像で埋めない。
4. 下の形で本文を書き、人に見せる
5. 人が「これで出して」と言ったら、ブランチを push して PR を作る
   - `git push -u origin <今のブランチ名>`（main には push しない）
   - `gh pr create --base main --title "<タイトル>" --body-file -`（本文は標準入力で渡す）
   - gh が使えなければ、本文を表示して、人に GitHub の画面で PR を作ってもらう。

## 本文の形

```markdown
## 何を変えたか
- （利用者から見て何が変わったかを1〜3行。ファイル名の羅列ではなく、できるようになったこと）

## どう確かめたか
- テスト: （テストのコマンド）で ○件すべて通った
- 手で確かめたこと: （人が答えた操作と結果。例: 追加の画面で名前を入れて追加すると、一覧の一番上に出た）

## スクリーンショット
<!-- 人が自分でアプリを操作して撮った画像を、ここに貼る（GitHub の画面でドラッグ＆ドロップ） -->

## レビューで見てほしいところ
- （迷ったところ、自信がないところ。無ければ「特になし」）
```

## 守ること

- タイトルは「何ができるようになったか」を短く書く（例: 「項目に締め切りを付けられるようにする」）。
- `.env` の中身、キー、個人情報を本文に書かない。
- スクリーンショットは人が撮って貼る。Claude は撮らない。欄は空けたままにして、人に「画像を貼ってください」と伝える。
- 1つの PR には1つの機能だけ。関係ない変更が混じっていたら、分けるかを人に聞く。
